# Frontend (`web/`)

Vite + React 19 + TypeScript SPA. The Gradle and npm toolchains are disjoint — never invoke npm from Gradle or vice versa.

- Dev server: `cd web && npm run dev` (port 5173). All backend routes live under the `/api/` namespace (`/api/v1/login`, `/api/v1/logout`, `/api/v1/users`, `/api/v1/teams`, `/api/v1/feedbacks`, …) and Vite proxies the single `/api` subtree → `http://localhost:8080`. Any other path is served as `index.html` so React Router owns the SPA URL space and browser reloads don't collide with API routes.
- Production build: `cd web && npm run build` → static files in `web/dist`. In the Docker image these are baked in and served by the Ktor server itself (via `WEB_STATIC_DIR`; see "Server bootstrap model" / `plugins/Routing.kt`), so production is single-origin and there is no Vite proxy — the SPA and `/api` share `http://localhost:8080`.
- Regenerate API types: `cd web && npm run gen:api`. Reads `server/src/main/resources/openapi/documentation.yaml` directly (no server needed) and writes `web/src/api/schema.ts`. Run this after editing the OpenAPI spec; commit the regenerated `schema.ts`.
- **Quality gates (the frontend counterpart of the backend's detekt)**: `npm run lint` carries `eslint-plugin-sonarjs` (recommended) plus core size/complexity backstops — zero-findings gate; rule tuning lives in `eslint.config.js` ONLY, one commented override per deliberate idiom (JSX conditional chains, the link-builder template idiom, single-function page components), and any inline `eslint-disable` needs a justifying comment. `npm run knip` is the dead-code gate (unused files/exports/dependencies; `knip.json` ignores the generated `schema.ts`) — keep exports that only the declaring file uses un-exported, and delete what knip flags rather than ignoring it.
- **Build version stamp**: `vite.config.ts` injects `__APP_COMMIT__` (short sha, `+dirty` when the worktree has uncommitted changes) and `__APP_COMMIT_TIME__` (commit ISO timestamp) via `define`, declared in `src/vite-env.d.ts`. Env vars `GIT_SHA`/`GIT_COMMIT_TIME` override the local-git lookup — the Dockerfile's SPA stage sets them explicitly (its worktree never matches the index, so the dirty check would false-positive), and CI can do the same when building without `.git`. `src/components/VersionStamp.tsx` renders the stamp (`7caf94e · 2026-07-03 14:22`) at the bottom of the navbar (`App.tsx`) and under the login card (`components/AuthCard.tsx`, shared by Login + ResetPassword since v1.35.0); tooltip label is `common.buildInfo`.

The OpenAPI spec at `server/src/main/resources/openapi/documentation.yaml` is the contract between backend and frontend — it is hand-maintained, not auto-generated from routes. When adding/changing a route, update the spec in the same change. Swagger UI is mounted at `http://localhost:8080/openapi`.

The typed API layer lives in `web/src/api/` as small hand-written modules: `http.ts` (transport — `authedFetch()` with the single-flighted silent refresh, `ApiError`, and the two standard wrapper shapes `jsonRequest<T>()`/`voidRequest()` every ordinary endpoint wrapper uses since 2026-08, plus `buildQuery()` — the list wrappers' query-string builder (skips null/undefined/""; `false` is sent, so an omit-when-false param like `includeIndirect` is passed as `value || undefined`) — reach for the raw `authedFetch`/`safeJson` primitives only when a wrapper genuinely inspects the Response), `session.ts` (token/roles/feature-flag storage and the render-time accessors like `isAdmin()`/`hasFeature()`), `auth.ts` (login incl. the MFA step, logout, password reset), and one thin endpoint-wrapper module per feature area (`users.ts`, `teams.ts`, `feedbacks.ts`, `goals.ts`, `pulse.ts`, …). The types come from the generated `schema.ts`; a new endpoint's wrapper goes into its feature's module (a new feature area gets a new module — never a catch-all file). Avoid pulling in heavyweight client generators (Orval/Kiota) — the lightweight pairing of `openapi-typescript` (types only) + hand-written fetch is intentional.

`openapi-typescript` is installed with `--legacy-peer-deps` because its declared peer is TS `^5` while the scaffold uses TS 6; the generated output is compatible. If you re-`npm install` from scratch, use `npm install --legacy-peer-deps`.

## Session isolation

`api/session.ts` owns session transitions and subscriptions. Login, logout, definitive refresh rejection, and a session replacement in another tab are boundaries: clear the QueryClient's query and mutation caches before notifying auth subscribers, and remount the authenticated subtree so the previous account's component/form state cannot survive. Keep this binding active for the whole app lifetime, including the login screen. Device preferences (`lettuce.lang`, view settings, changelog seen state) retain their existing lifetime.

Asynchronous authentication and transport work must capture its originating session and check that it is still current before committing credentials, clearing a session, retrying an authenticated request, or returning data. Check stored identity/credentials as well as the local generation: another tab can update storage before its `storage` event is delivered. Refresh single-flight belongs to the captured session; completion of an old flight must never reset a newer flight. A normal refresh within the current session preserves caches and mounted forms. If refreshed roles or disabled features change, reset the boundary so cached privileged data, navigation, and page guards reflect the new authorization state.

Logout clears local state immediately, including when there is no access token, then attempts server revocation with the captured credentials. Callers must not defer cache clearing, auth notification, or navigation until the revoke request completes: the user may already have signed in again. Only a definitive refresh rejection ends the session; network, timeout, 429, 5xx, and malformed refresh responses keep it available for retry.

## Changelog & app versioning

The user-facing changelog is a **build-time artifact** — no DB, no API, changes only with a deploy. `web/src/changelog/entries.ts` holds `ChangelogEntry` rows (`version`, `date` `YYYY-MM-DD`, `en`/`pl` **markdown** bodies), newest first; the app's only human-readable version is `APP_VERSION` in **`web/src/changelog/version.ts`** — its own tiny module so the shell's eager imports (VersionStamp, the what's-new dot) never pull the ~170 KB bilingual entries into the main bundle (the entries ride the lazy Changelog chunk only, 2026-08 CR-012). **A release = the new entry at the top of entries.ts + the bump of that one literal** (the Gradle `1.0.0-SNAPSHOT` is unrelated); `entries.test.ts` pins `CHANGELOG[0].version === APP_VERSION`, so forgetting either half fails the suite. Release convention:

- Write both language bodies by hand (or LLM) — never derive them from commit messages. Bodies are *content*, so they live in the data file, not `locales/`; the PL body follows the Polish style rules below (declined loanword `feedback`, inclusive slash forms, active voice).
- Keep dates descending (same-day releases are fine — newest stays on top), versions unique, and both bodies non-empty — pinned by `web/src/changelog/entries.test.ts`.
- Keep phrases that tests assert on in plain text runs: markdown formatting splits text nodes, and testing-library's `getByText` matches direct text nodes only.

Rendering & UI wiring:

- `pages/Changelog.tsx` (`/changelog`, authenticated, lazy) renders the entries as a Mantine `Timeline` with `MarkdownView` bodies in the viewer's language, and calls `markChangelogSeen()` on mount. **Bodies are authored EN+PL only, by policy** — a new shipped UI language does NOT add changelog fields; non-authored languages read the English body (`AUTHORED_LANGUAGES` in the page).
- `components/VersionStamp.tsx` shows `v<APP_VERSION> · <sha> · <time>`; its optional `to` prop renders it as a router link — the navbar instance links to `/changelog`, the Login instance deliberately stays plain (the route is behind auth). A "Changelog" nav item (`CHANGELOG_NAV` in `App.tsx`) is pinned last, directly above the stamp.
- The **"what's new" dot** is a red Mantine `Indicator` around the navbar stamp in `App.tsx`, shown while localStorage `lettuce.changelog` (`{seenVersion}`) differs from `APP_VERSION`. It's driven by `hooks/useChangelogSeen.ts` via `useSyncExternalStore` over a module-level listener set — do **not** replace that with a plain localStorage read in state: the shell renders before the page's mark-seen effect, so the dot would only clear on the next navigation. The seen-state is device-level (survives logout, like `lettuce.lang`) and hand-rolls its guarded read/write (the `AlertsBanner` pattern), not `useStoredState` (that hook owns the `lettuce.viewSettings.*` namespace).
- Tests: `pages/Changelog.test.tsx`, `changelog/entries.test.ts`, the dot/nav cases in `App.test.tsx`, and the link/prefix cases in `components/VersionStamp.test.tsx`.

## Error handling (v2.22.0)

The SPA is expected to fail gracefully under every failure class — render crashes, dead chunks, unmatched URLs, timeouts, a downed backend. The seams, and the rules that keep them working:

- **ErrorBoundary** (`components/ErrorBoundary.tsx`): a page render crash must never white-screen the app. `RouteErrorBoundary` wraps the `<Outlet />` inside `AppShell.Main` (header/nav survive; keyed by `location.pathname`, so navigating anywhere recovers), and a plain `ErrorBoundary` in `main.tsx` is the last resort for shell crashes. Don't add per-page boundaries — the two mounts are the model.
- **Catch-all 404**: `pages/NotFound.tsx` is registered as the LAST `path="*"` child of the Shell route and is deliberately not feature-gated. New routes go above it.
- **Chunk-load recovery**: `main.tsx` listens for `vite:preloadError` (a redeploy 404s the old hashed chunks) and reloads once, rate-limited via sessionStorage (max one reload/minute) so a genuinely missing chunk falls through to the ErrorBoundary instead of looping.
- **Timeouts**: every transport fetch carries `timeoutSignal()` (`api/http.ts`, 30 s, feature-detected for happy-dom) — a hung request rejects with a `TimeoutError` DOMException instead of pending forever. Callers may pass their own `signal` to override; new `fetch` call sites in `api/` must attach it.
- **Refresh survives transient failures**: `doRefresh` distinguishes a DEFINITIVE rejection (no refresh token, or the server answered 401/403 → session cleared, signed-out flag) from a TRANSIENT one (network/timeout/5xx/the refresh bucket's 429/malformed body → session KEPT; the caller sees the original 401 and can retry). Never collapse the two — pre-v2.22.0 a network blip during refresh erased a valid session. `logout()` is best-effort: the revoke POST may fail, `clearSession()` always runs, the function never throws.
- **Query retry policy**: the `QueryClient` in `main.tsx` uses `shouldRetryQuery` (`api/http.ts`) — NEVER retry a 4xx (the answer won't change; retrying only delays the error UI), at most two retries for transient failures. Per-site `retry: false` on detail pages predates this and is harmless; don't add new ones just to dodge retries on 4xx.
- **Messages**: never render `error.message` (it's the internal `API <status>` / the browser's "Failed to fetch"). List/read failures → `loadErrorMessage(err, t)` (`utils/saveError.ts`; timeout/network/status-specific bodies from `common.error.*`); mutations stay on `saveErrorMessage` (which also maps timeouts now). ProblemDetail access goes through the `ApiError.detail`/`ApiError.instance` getters — no hand-casting `err.body`.
- **Partial failures are itemized and retryable (v2.24.0)**: a multi-item mutation never reports one generic error. `useBulkFeatureUpdate` keeps the failed rows' identity (`failed` + `retry()` — FeatureFlags names them and retries exactly them); RequestFeedback creates sequentially, prunes successes from the selection, and lists each failure with its reason — new multi-item flows follow this shape, never `Promise.all` + one catch.
- **No silent blanks (v2.24.0)**: a failed load must not look like an empty result. The history components share the `components/EventTimeline.tsx` shell (v2.30.0 — spinner, `loadErrorMessage` Alert, empty note, the Timeline; each area keeps only its query + `describeEvent`), and `TeamKpiChart` renders a `loadErrorMessage` Alert on error; the picker hooks (`useAllUsers`/`useManagerOptions`/`useManagedReports`/`useDictionaryOptions`) expose an error flag that FORM pickers surface as the Select's `error` (`common.error.optionsFailed`) — filter pickers deliberately degrade to unfiltered instead. `PulseSettingsCard` flags a failed settings load (its form shows defaults otherwise). Dictionary's saved-but-stale state (PUT committed, re-read failed) freezes the editor behind a reload prompt — a resubmit without the minted ids would insert duplicates.
- **Route transitions stay inside the shell (v2.24.0)**: the `Suspense` around the Shell's `<Outlet />` keeps header/nav mounted while a lazy page chunk loads; the App-level Suspense only covers the unauthenticated pages.

## Shared list-page building blocks

The list views come in two shapes — **tables** (Users, Teams, Templates, FeedbackTable: long, paginated, filterable) and **person-card grids** (the dashboard's ManagersTable and TeamMembersTable: a handful of people as `PersonCard`s in a responsive `SimpleGrid` rendered as a semantic `<ul>`). Both are built from shared pieces — a new list should reuse them rather than re-declaring the scaffolding:

- **Infinite scroll (v2.2.0, one instance so far)**: `pages/Kudos.tsx` is the repo's only `useInfiniteQuery` list — a filter-less, pager-less timeline that loads the next page when a sentinel `Box` enters the viewport (`useIntersection` from `@mantine/hooks`, `getNextPageParam` from `page * pageSize < total`). Testing caveat: happy-dom has no layout, so `IntersectionObserver` never fires — stub it globally and drive the callback by hand (`Kudos.test.tsx` is the template). ## Per-user feature flags (v1.53.0)

Admin-set per-user flags over the feature areas (`FEEDBACKS`/`ONE_ON_ONES`/`GOALS`/`TEAM_KPIS`/`PERFORMANCE_REVIEWS`/`DAYS_OFF`/`PULSE_SURVEYS` since v2.0.0/`IMPACT_LOG` since v2.36.0/`SUCCESSION_PLANS` since v2.42.0, plus the special `MFA` value since v2.4.0 — the `FEATURES` const in `api/session.ts`; **MFA is login-only and inverted-default**: every user starts with it disabled (opt-in email second factor), it gates no nav leaf, page, card, or tour stop — the two flag editors and the users-list filter are its only SPA surfaces); a disabled feature must not be visible anywhere for that user (the server separately 403s its routes; caller-only semantics — the flags gate the SESSION USER, never the person a card/row is about). ## Internationalization (i18n)

The SPA is **N-language by architecture** (v2.20.0) via **react-i18next** (`web/src/i18n.ts`); the shipped bundles are English (THE default and fallback everywhere) and Polish, with neither special-cased beyond that. All user-facing strings go through `const { t } = useTranslation()` / `<Trans>` — **no hardcoded UI text**. Conventions:

- **The language set is the build-time constant `SUPPORTED_LANGUAGES` in `i18n.ts`**, mirrored by the server's `dictionaries/Languages.kt` (they must agree — the server validates dictionary payload language keys against it). Only EN is statically imported (its typed `en` tree is the key canon AND the runtime fallback); every other language's bundle is auto-discovered from `locales/<lang>/` via `import.meta.glob` (the `AREA_MOUNT` map handles the four filename≠area cases). **Adding a language** = a complete `locales/<lang>/` folder (26 area files, parity-gated) + one code in `SUPPORTED_LANGUAGES` + one `NATIVE_LANGUAGE_NAMES` line + `common.languageName.<lang>` in EVERY language's common.json + one `EMOJI_I18N` line in `components/EmojiPicker.tsx` + one `dayjs/locale/<lang>` import in `components/AppDatesProvider.tsx` (the calendar locale, v3.5.0) + the server constant + a parameter on the server's `LocalizedText` (every email text becomes a compile error until translated) — the Record types, the parity test, and the Kotlin compiler each fail loudly on a missed step. Bundles are **eager** on purpose (~95KB raw per language in the main chunk); move non-EN bundles to lazy loading when a 3rd language ships or a bundle passes ~150KB.
- **Server-carried localized content** (dictionary entries, the career triple, pulse rotating-question snapshots) arrives as `values: {lang: value}` maps with `en` always present; **every display site resolves through `pickLocalized(values, lang)` in `utils/localized.ts`** (blank-guarded EN fallback) — never index a values map directly. Dictionary editing is EN-required/others-optional (`utils/dictionaryForm.ts`; a blank non-EN input is omitted from the PUT — the server's omit-to-clear contract); the editor shows English beside ONE picker-chosen translation column and the read-only view a per-entry language-count badge with a popover (v2.23.0 — both constant-width at any language count).
- **Emails are language-specific since v2.21.0**: every server-composed email (password reset, MFA code, welcome, notification mirror) renders in the RECIPIENT'S stored language (V61 `users.language`, EN fallback) — the server-side texts live as `LocalizedText(en, pl)` values (`infra/mail/LocalizedText.kt`), whose constructor arity is the server's parity gate. **The user language is ONE synced property**: the header switcher saves it to the server on switch (`setUserLanguage`), and `persistSession` applies the login/refresh response's `language` to the UI — so signing in restores the user's language on any device, and an admin change propagates at the ≤15-min silent refresh.

- **Resources** live in `web/src/locales/{en,pl}/<area>.json`, one file per area (`common`, `appShell`, `auth`, `dashboard`, `feedback`, `kudos`, `oneOnOne`, `goals` — mounted as area `goal` — `teamKpis` — mounted as area `teamKpi` — `performanceReviews` — mounted as area `performanceReview` — `daysOff`, `pulse`, `users`, `teams`, `templates`, `dictionaries` — mounted as area `dictionary` — `notifications`, `emailNotifications`, `alerts`, `changelog`, `tour`, `org`, `career`, `impactLog`, `succession`, `integration` — the v3.0.0 integration-clients admin screen); `i18n.ts` merges them into a single `translation` namespace, so keys read `area.key` (e.g. `t("feedback.editTitle")`). **Keys are typed**: `src/i18next.d.ts` augments i18next's `CustomTypeOptions` with `typeof en` from `i18n.ts` (the `@public`-tagged export — knip can't trace the d.ts consumer), so every `t()` call and `i18nKey` is compile-checked against the EN tree — a typo or removed key fails `tsc`/`npm run build`. Conventions that keep it working: fields holding a key are typed `ParseKeys` (from `i18next`), never `string` (the `labelKey`/`successKey`/nav-label pattern); functions taking a translator take `TFunction`, never a hand-written `(key: string) => string`; dynamic keys built from a statically known union type-check as-is, and the few genuinely dynamic sites (wire enum values in history/notification renderers) go through `dynamicKey` in `utils/i18nKey.ts` — use it only when the union is truly unknowable to TS, never to silence a typo; test stubs cast via `as unknown as TFunction`.
- **`common.*` is the shared source**: actions, field labels, table/pagination, filters, and the enum labels `common.status.*` / `common.visibility.*` / `common.role.*`. Reuse it instead of duplicating; build Mantine `Select` option labels from `t()` at render so they translate.
- **Creation-verb convention (v1.15.2):** buttons that open a create screen say **"New <thing>"** / PL **"Nowy/Nowa/Nowe <thing>"** (New team, New user, New template, New feedback, New alert, New 1:1, New goal, New team KPI — and the create screens' titles reuse the same wording); in-form list adders say **"Add …"** / **"Dodaj …"** (Add point, Add a provider, Add to team); the create form's submit button is the bare `common.action.create` **"Create"** / **"Utwórz"**. New buttons must pick the tier that matches their behavior, not mix verbs.
- **Keep key parity vs EN for every shipped language** — a shipped bundle is all-or-nothing: every English key must exist in each `locales/<lang>/` (language-specific plural variants like PL's `_few`/`_many` are expected), enforced by `locales/parity.test.ts` (auto-discovers language folders; also pins folders == `SUPPORTED_LANGUAGES`). Use i18next interpolation (`{{name}}`) and plural keys (`_one/_few/_many/_other`) rather than string concatenation.
- **Polish term for "feedback" is the loanword `feedback`, declined** (feedback / feedbacku / feedbacki / feedbacków), *not* "opinia". `teams.json` is the style reference.
- **Polish voice/gender convention:** **inclusive slash forms**, active/direct voice, same tense and meaning as the English — 3rd person `"{{provider}} odmówił/a…"`, 2nd person `"Poprosiłeś/aś…"`, participles `"wylogowany/a"`. Spell out irregular feminines in full (e.g. `"usunął/usunęła"`, never `"usunął/a"`). Do **not** use impersonal/passive dodges (`"Poproszono…"`, `"Wylogowano Cię"`).
- **Tests** render English: `web/src/test/setup.ts` imports `../i18n` and forces `en`, and English keys resolve byte-identically to the old literals, so text-based assertions keep working. Every test `MantineProvider` (the shared `src/test/render.tsx` wrapper and each file-local one) must pass **`env="test"`** — since Mantine 9.4 the Popover/Combobox dropdown is `display: none` until Floating UI's `hide` middleware sees a real bounding box, which never happens in happy-dom, so Select-option clicks silently fail without it. The language switcher is `web/src/components/LanguageSwitcher.tsx` (header) — a Mantine `Menu` of NATIVE language names (`NATIVE_LANGUAGE_NAMES`, deliberate constants: readable before switching, and `Intl.DisplayNames` yields lowercase forms); choice persists in `localStorage` (`lettuce.lang`) and updates `<html lang>`.
- **Scope:** frontend chrome is translated, and both **feedback history events** and **notifications** are localized client-side — the server stores them structurally (`type` + `params`), with no rendered string (see `.claude/docs/features/feedbacks.md` / `.claude/docs/features/notifications.md`). No server-generated user-facing text remains English.
