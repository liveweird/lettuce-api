### Notifications

In-app notifications are **typed structured rows** (`recipientId`, `type`, `params`, optional `link`, `wasSeen`, `timestamp`) and there is no API to create one. Like feedback events, no rendered string is stored: `type` is a `NotificationType` (`notifications/Notification.kt` — 48 values: 13 feedback-driven, e.g. `FEEDBACK_SENT_TO_SUBJECT`, the `FEEDBACK_REQUEST_EXPIRED_TO_REQUESTER`/`_TO_PROVIDER` pair (v3.8.0 — the lazy expiry sweep, see "Feedback request expiration" in `.claude/docs/features/feedbacks.md`), the `ONE_ON_ONE_CREATED_TO_SUBORDINATE`/`_TO_MANAGER` pair — see "1:1 meetings" in `.claude/docs/features/one-on-ones.md` — the six goal values (the four transition `GOAL_*_TO_SUBORDINATE` values plus the v2.8.0 progress-update pair `GOAL_PROGRESS_UPDATED_TO_MANAGER`/`_TO_SUBORDINATE`) — see "Goals" in `.claude/docs/features/goals.md` — the seven team-KPI `TEAM_KPI_*_TO_MEMBER` values (four transitions + the three data-point mutations) — see "Team KPIs" in `.claude/docs/features/team-kpis.md` — the `PERFORMANCE_REVIEW_PUBLISHED/UNPUBLISHED_TO_SUBORDINATE` pair — see "Performance reviews" in `.claude/docs/features/performance-reviews.md` — the nine days-off values (`DAYS_OFF_REQUESTED/CANCELLED_TO_MANAGER`, `DAYS_OFF_ACCEPTED/REJECTED/CORRECTED/CANCELLED_TO_OWNER` — the cancelled pair reworked v2.31.0 with the `by` OWNER/MANAGER context — the v2.29.0 on-behalf pair `DAYS_OFF_RECORDED_TO_OWNER`/`_TO_MANAGER`, and `DAYS_OFF_ALLOWANCE_CHANGED` (v2.32.0) — see "Days off" in `.claude/docs/features/days-off.md`) — the four pulse values (`PULSE_CYCLE_SCHEDULED/OPENED/CANCELLED`, `PULSE_RESULTS_AVAILABLE` — see "Pulse surveys" in `.claude/docs/features/pulse-surveys.md`) — the three impact-log `IMPACT_ENTRY_CREATED/UPDATED/DELETED_TO_MANAGER` values (v2.36.0 — see "Impact log" in `.claude/docs/features/impact-log.md`) — `CAREER_POSITION_STARTED_TO_USER` (v2.15.0 — see "Career progression" in `.claude/docs/features/dictionaries.md`) — and `PASSWORD_CHANGED`) and `params` is a JSON map of the **party names** (proper nouns) the message interpolates. The SPA renders each in the viewer's language (`web/src/components/NotificationsButton.tsx` `describeNotification` → `notifications.event.*` keys; the `self` param is the generic i18next-context carrier — `"self"`/`"reflection"` for the legacy self-reflection wordings (stored rows only since v2.36.0), `"admin"`/`"reset"` on `PASSWORD_CHANGED`). The feedback-driven ones are produced by **four** sources, all side-effect-free (DB-free, so directly unit-testable) functions in `feedbacks/FeedbackNotifications.kt`; `FeedbackService` resolves party display names into `params` (plus, for SENT landings, the subject's **direct managers** via `teams/ManagementChain.kt` `directManagerIds` — they gain read access at delivery) and the route persists what they return:

- **`feedbackCreationNotifications()`** — on feedback **creation**. In `REQUESTED` status: the **provider** is told (edit link) **and** the **requester** gets a no-link confirmation (worded "about yourself" when requester == subject). Created directly as `SENT` ("save & send", no draft step): the same set as the `DRAFT → SENT` transition — subject + provider (+ requester if present) — via shared `sentTo*Note` builders, so the recipients never depend on whether a draft step happened. A `DRAFT` creation mints nothing. Persisted from `POST /api/v1/feedbacks` in `feedbacks/FeedbackRoutes.kt` (`result.notifications.forEach { notificationService.create(it) }`).
- **`feedbackTransitionNotifications()`** — on a feedback **status transition**. Persisted from the POST action endpoints (`…/{id}/send|withdraw|reject|pick-up`, shared `transitionTo` handler: `toNotify.forEach { notificationService.create(it) }`).
- **`feedbackDeletionNotifications()`** — on a (DRAFT) feedback **deletion** that has a requester. Persisted from `DELETE /api/v1/feedbacks/{id}`; the notification has no link.
- **`feedbackExpiredToRequesterNotification()`** / **`feedbackExpiredToProviderNotification()`** (v3.8.0) — on the **lazy expiry sweep** (`FeedbackService.expireOverdueRequests`, no background job — the `AlertService.visible(now)` precedent): a `REQUESTED` row whose `expiresOn` deadline has passed auto-rejects, and both notify. Persisted at the **top of `GET /api/v1/feedbacks`**, alongside the row's `REQUEST_EXPIRED` audit event — same pattern as the transition POSTs, just triggered by a GET rather than a POST (the `TokenBlocklistService` "clean up during the next call" precedent). See "Feedback request expiration" in `.claude/docs/features/feedbacks.md`.

**The complete list of situations that generate a notification**:

| Event | Recipient(s) | Link? |
|---|---|---|
| Created in `REQUESTED` | provider; **and** the requester (always — `REQUESTED` requires one) | provider → `/feedback/{id}/edit` (always); requester → **no link** |
| Created in `SENT` ("save & send") | same as `DRAFT → SENT` below | same as `DRAFT → SENT` below |
| `DRAFT → SENT` | **every recipient** (one note each, always — up to four since v3.1.0); the **provider** (the sender, always); the requester if `requesterId != null` (separately-worded notifications); **and** the **direct managers of every recipient** (they gain read access at delivery; a manager who is themselves a party — provider, recipient, or requester — is excluded) | subject/requester → `/feedback/{id}/view` only if that recipient may read the feedback; provider → `/feedback/{id}/view` (always — owns it); managers → `/feedback/{id}/view` (always — manager read on delivered feedback is not visibility-gated) |
| `REQUESTED → REJECTED` (requester present) | requester | no |
| `REQUESTED → DRAFT` ("picked up" by provider) | requester | no |
| `SENT → WITHDRAWN` **or** `DRAFT → WITHDRAWN` (abandon — either way the record lands, delivered, in the recipients' Received lists) | **every recipient** (one note each, always); **and** the requester if `requesterId != null` | no |
| `DRAFT` deleted (requester present) | requester | no |
| `REQUESTED` request auto-rejected past its `expiresOn` deadline (v3.8.0 — the lazy sweep, `FeedbackService.expireOverdueRequests`, run at the top of `GET /api/v1/feedbacks`; requires a requester by rule) | the **requester** (`FEEDBACK_REQUEST_EXPIRED_TO_REQUESTER`) **and** the **provider** (`FEEDBACK_REQUEST_EXPIRED_TO_PROVIDER`); params `{requester, provider, subject}` on both (the `FEEDBACK_REJECTED_TO_REQUESTER` shape) | no |
| Password changed — self-change, admin reset of another user, or self-service email reset | the affected user (`PASSWORD_CHANGED`; `self` param absent / `"admin"` / `"reset"` picks the wording) | no |
| 1:1 meeting created | the subordinate (`ONE_ON_ONE_CREATED_TO_SUBORDINATE`) **and** the manager/author (`ONE_ON_ONE_CREATED_TO_MANAGER`) | both → `/one-on-ones/{id}/view` |
| Goal status transition (activate / deactivate / archive / reopen) | the subordinate (`GOAL_ACTIVATED/DEACTIVATED/ARCHIVED/REOPENED_TO_SUBORDINATE`; params `{manager, title}` — the goal title is plaintext by design) | `/goals/{id}/view` |
| Goal progress update (v2.8.0 — value change or comment-only; a true no-op mints nothing) | the **counterparty** of the actor: subordinate updates → the manager (`GOAL_PROGRESS_UPDATED_TO_MANAGER`, params `{subordinate, title}`), manager updates → the subordinate (`GOAL_PROGRESS_UPDATED_TO_SUBORDINATE`, params `{manager, title}`); the comment itself never rides along (encrypted on the event) | `/goals/{id}/view` |
| Team-KPI status transition (activate / deactivate / archive / reopen) | **every current member + the team's current manager, minus the ACTOR** (v2.26.0 — the actor may be a chain manager; `TEAM_KPI_ACTIVATED/DEACTIVATED/ARCHIVED/REOPENED_TO_MEMBER`; params `{manager, title, team}` — the `manager` key carries the ACTOR's name; title and team name are plaintext by design) | `/team-kpis/{id}/view` — except deactivate (**no link**: the KPI lands back in DRAFT, unreadable for members) |
| Team-KPI data-point mutation (add / correct / remove — v1.30.0; an exact no-op correction mints nothing) | **every current member + the team's current manager, minus the ACTOR** (v2.26.0 — members and chain managers record data too; `TEAM_KPI_VALUE_RECORDED/CORRECTED/REMOVED_TO_MEMBER`; params `{manager, title, team, kpiType}` + `{date, value}` or `{fromDate, fromValue, toDate, toValue}` — the `manager` key carries the ACTOR's name; raw ISO dates/Double strings, formatted client-side per `kpiType`) | `/team-kpis/{id}/view` (always — values only mutate while ACTIVE, which members read) |
| Performance review published (`CALIBRATION → PUBLISHED`) | the subordinate (`PERFORMANCE_REVIEW_PUBLISHED_TO_SUBORDINATE`; params `{manager, startMonth, endMonth}` — raw ISO months, formatted client-side) | `/performance-reviews/{id}/view` |
| Performance review un-published (`PUBLISHED → CALIBRATION`) | the subordinate (`PERFORMANCE_REVIEW_UNPUBLISHED_TO_SUBORDINATE`; same params) | **no link** (the review is no longer readable to them — the KPI-deactivate precedent) |
| Days-off request created | **every current direct manager** of the owner — deliberately NOT the whole chain, though the chain may resolve since v2.33.0 (the chain right is pull, not push) — (`DAYS_OFF_REQUESTED_TO_MANAGER`; params `{requester, type, pool?, days, startDate, endDate}` — `pool` = the paid pool's name (v3.2.1, PAID only), rendered in place of the type word by the SPA and the email — raw ISO dates / a "1.5"-style days string / the enum name, formatted client-side) | `/days-off?tab=team` |
| Days-off request accepted / rejected | the owner (`DAYS_OFF_ACCEPTED/REJECTED_TO_OWNER`; params `{manager, startDate, endDate}`) | `/days-off?tab=requests` |
| Days-off request cancelled (v2.31.0 — by the owner OR a chain manager, always with a stored encrypted reason that NEVER rides params) | the **owner**, always — even as the actor (`DAYS_OFF_CANCELLED_TO_OWNER`; params `{manager (the actor), by OWNER\|MANAGER, startDate, endDate}` — `by` is the i18next context) | `/days-off?tab=requests` |
| — the manager side of the same cancellation | owner-cancel → **every current direct manager**; manager-cancel → the **acting manager's receipt** only (`DAYS_OFF_CANCELLED_TO_MANAGER`; params `{requester, manager, by, startDate, endDate}`) | `/days-off?tab=team` |
| Days-off budget correction created (edits/deletes silent) | the subordinate (`DAYS_OFF_CORRECTED_TO_OWNER`; params `{manager, pool, year, operation, days}` — the SPA words ADD/SUBTRACT via i18next context; `pool` = the adjusted paid pool's name since v3.2.0, pre-pool rows carry none and the SPA/email fall back to the default pool's wording) | `/days-off?tab=requests` |
| Days-off allowance set or changed (v2.32.0 — a chain manager writes ONE paid pool's yearly allowance; a fresh extra-pool grant is this same event, v3.2.0; idempotent re-PUTs silent) | the target user (`DAYS_OFF_ALLOWANCE_CHANGED`; params `{manager, pool, to}` + `from` only when previously set) | `/days-off?tab=requests` |
| Days off recorded on behalf (v2.29.0 — a chain manager creates a report's entry, chain-wide since v2.33.0, born ACCEPTED) | the **owner** (`DAYS_OFF_RECORDED_TO_OWNER`; params `{manager, type, pool?, days, startDate, endDate}` — `pool` as on the request note, v3.2.1) **and** the **acting manager** (`DAYS_OFF_RECORDED_TO_MANAGER`; params `{requester, type, pool?, days, startDate, endDate}` — a durable receipt, see the boundary rule below); other managers — the direct ones included when a chain manager records — deliberately get nothing (the row shows in their managed list) | owner → `/days-off?tab=requests`; manager → `/days-off?tab=team` |
| Pulse cycle scheduled | every currently ELIGIBLE user (`PULSE_CYCLE_SCHEDULED`; params `{openDate, closeDate}` — computed at schedule time, un-stored) | no (no survey exists yet) |
| Pulse cycle opened | the snapshotted participants (`PULSE_CYCLE_OPENED`; params `{closeDate}`) | `/pulse?tab=survey` |
| Pulse cycle closed | **respondents only** (`PULSE_RESULTS_AVAILABLE`; params `{closeDate, cycleId}`) | `/pulse?tab=results&cycle={id}` |
| Pulse cycle cancelled **from OPEN only** (scheduled/closed cancel silently) | the participants (`PULSE_CYCLE_CANCELLED`; params `{openDate}`) | no |
| Impact log entry created / updated / deleted (v2.36.0 — always by the journal's owner; a no-op PUT mints nothing) | the owner's **direct managers only** (never the acting owner; the chain above reads on demand — the fan-out-stays-direct rule; a manager-less owner notifies nobody) (`IMPACT_ENTRY_CREATED/UPDATED/DELETED_TO_MANAGER`; params `{author, periodStart, periodEnd}` — raw ISO dates, formatted client-side; section texts are encrypted and NEVER ride params) | created/updated → `/impact-log/{id}/view`; deleted → `/impact-log?tab=managed` (the entry's view would 404) |
| Career position started (v2.15.0 — a chain manager records a new position; corrections/deletes silent, the corrections precedent) | the user (`CAREER_POSITION_STARTED_TO_USER`; params `{manager, startDate}` — raw ISO date, formatted client-side; the position's values are behind the link, never in params) | `/users/{recipientId}/career` |

That is the whole set — any other feedback create/transition/delete, 1:1 edit/deletion, goal create/definition-edit/deletion (progress updates DO notify since v2.8.0 — see the row above), team-KPI create/definition-edit/deletion, performance-review create/edit/deletion (and its `DRAFT ↔ CALIBRATION` transitions — invisible to the subordinate), review-period or public-holiday mutation, days-off correction edit/deletion, career-position correction/deletion (only STARTING one notifies — see the row above), pulse response submission/edit or pulse settings/date change, an impact-log no-op PUT, or user mutation (allowance changes included) produces nothing. The non-feedback notifications are the 1:1 creation pair (`oneonones/OneOnOneNotifications.kt`), the goal set (`goals/GoalNotifications.kt` — transitions subordinate-only, the manager is always the actor; progress updates counterparty-directed, either party may act since v2.8.0), the team-KPI sets (`teamkpis/TeamKpiNotifications.kt` — transitions + data-point mutations, members-only, actor excluded; the value notifications are composed route-side from the pre-mutation read + `TeamKpiService.memberIds`), the performance-review publish/unpublish pair (`reviews/PerformanceReviewNotifications.kt` — subordinate-only, the manager is always the actor), the days-off set (`daysoff/DaysOffNotifications.kt` — manager-directed on create/cancel, owner-directed on resolution, both-parties on an on-behalf recording (v2.29.0); recipients resolved in the service transaction), the pulse cycle set (`pulse/PulseNotifications.kt` — pure builders, recipients resolved in the cycle service's transaction, persisted via the batch `NotificationService.createAll`; the acting admin is excluded), the career-position start (v2.15.0 — the descriptor builder in `users/CareerPosition.kt`, the manager name resolved in `CareerPositionService.create`'s transaction, persisted by `users/CareerPositionRoutes.kt`; feature mapping `null` — the users area is ungated), the impact-log set (v2.36.0 — `impactlog/ImpactLogNotifications.kt`, pure builders; recipients — the owner's direct managers — resolved in the service's mutation transaction), and `PASSWORD_CHANGED` (minted inline by `users/UserRoutes.kt`'s PUT-password handler and `auth/AuthRoutes.kt`'s reset completion — before the `password_reset.completed` audit event, which tests use as a completion barrier). For **legacy self-reflection rows** (provider == subject — no longer creatable since v2.36.0, see "Feedback lifecycle" in `.claude/docs/features/feedbacks.md`) every subject/provider-directed notification above is dropped (that recipient is the acting user); requester- and **manager**-directed ones remain, self-worded (the manager is never the actor) — so a standalone self row notifies only the author's managers, and a requested one additionally the requester. A `REQUESTED` creation yields **two** notifications (provider + requester); landing in `SENT` — whether via `DRAFT → SENT` or a direct "save & send" creation — yields **one per recipient + the provider** or, with a requester attached (single-recipient by rule), **three** (subject + provider + requester), plus one per direct manager of any recipient. **The `subject` param rule for a multi-recipient feedback (v3.1.0)**: a note addressed TO a recipient (`FEEDBACK_SENT_TO_SUBJECT`, `FEEDBACK_WITHDRAWN_TO_SUBJECT`) carries that recipient's OWN name; a MANAGER's note (`FEEDBACK_SENT_TO_MANAGER`) names only the recipients who report to THAT manager (v3.1.1 — its template says "who reports to you"; `FeedbackService.resolveSubjectManagers` hands the fan-out a manager→recipients map); every other note (provider, requester, rejected/picked-up/deleted) carries all recipients' names joined with `", "` in position order (`Feedback.subjectLabel`) — identical to today's value for one recipient, so the `notifications.event.*` templates and the email catalog interpolate unchanged. For the subject/requester `view` links the recipient must be permitted to read the feedback under its `FeedbackVisibility` (`subjectCanRead`/`requesterCanRead` in the same file) — otherwise `link` is null; the provider always owns the feedback and managers always read delivered feedback, so those links are unconditional.

**Notifications vs. the SPA's success toasts — the boundary rule.** A toast (`showSuccessToast`, see `web/CLAUDE.md`) is the **actor's** ephemeral client-side confirmation that their own mutation succeeded; a notification is persistent **counterparty** awareness of an event they wouldn't otherwise see. One event routinely produces both (the manager who activates a goal gets a toast, the subordinate a notification), and recipient sets exclude the actor as a rule. The four deliberate actor-directed exceptions are **durable receipts**, where a 2.5-second toast isn't enough of a record: feedback landing in `SENT` notifies the **provider** ("you sent this", with the view link), 1:1 creation notifies the authoring **manager**, an on-behalf days-off recording notifies the acting **manager** (v2.29.0 — a write to someone else's leave record deserves a persistent receipt), and `PASSWORD_CHANGED` fires even on a self-change (a security notice is valuable precisely as a persistent row). A new notification type directed at the acting user must justify itself the same way; otherwise the actor's toast is the whole confirmation.

**Email mirror (v2.3.0).** Every minted notification is also sent to the recipient's email address — immediately, one email per notification. The hook is the mint chokepoint itself: `NotificationService.create`/`createAll` insert the row(s), then hand the batch to `notifications/NotificationEmailer.kt` (constructed in `configureDatabase`; `configureMail` runs earlier, so the transport and `mail.appUrl` are readable), which fires **one fire-and-forget launch on the Application scope** per batch — never on the request path; a send failure is only logged (`ch.nokillswit.mail` logger; no queue/retry/outbox, the house mail posture). The wording lives in `notifications/NotificationEmail.kt` — a pure, DB-free per-language catalog mirroring the SPA's `notifications.event.*` strings, rendered in the RECIPIENT'S language since v2.21.0 (V61 `users.language`, read fresh at send time; EN fallback). Every text is an `infra/mail/LocalizedText(en, pl)` — the exhaustive `when` means **a new NotificationType will not compile without wording**, and the LocalizedText constructor arity means **a new language will not compile without translating every email text**. Per-area single-language subjects, the i18next context variants replicated (`self`/`reflection`, `admin`/`reset`, ADD/SUBTRACT), raw ISO dates/values (documented simplification — the SPA formats per locale), and the deep link appended as `mail.appUrl + link` only when both exist. Send-time skip rules, each against a fresh `UserService.read` per recipient:

| Condition | Effect |
|---|---|
| `mail.transport=disabled` (null mailer — the k8s default) | no emails at all, silently (email is a side effect, never 503) |
| recipient soft-deleted or deactivated | skipped |
| the type's `feature` ∈ the recipient's disabled set | skipped (mirrors the list read-filter; minting itself is never suppressed) |
| recipient opted out (`users.email_notifications_enabled = false`, V51) | skipped |
| catalog returns null (`PASSWORD_CHANGED` with `self="reset"` — the reset email IS the notice) | skipped |

The opt-out is **on by default** and self-service: `PUT /api/v1/users/{id}/email-notifications` `{enabled}` (target user or ADMIN — `requireSelfOrAdmin`, the self-service sibling of the ADMIN-only features PUT; idempotent; deactivated target allowed; audited `user.email_notifications_changed` on an actual change), surfaced as `UserResponse.emailNotificationsEnabled` and in the SPA as the header account-menu item → `/users/:id/email-notifications` (`pages/EmailNotifications.tsx`, one Switch). The flag is read **at send time**, so a change takes effect immediately — deliberately unlike the JWT-riding feature flags. Tests: `NotificationEmailTest` (catalog), `NotificationEmailDeliveryTest` (skip matrix, deterministic via a joined coroutineScope + one route-level pass), `UserEmailNotificationsTest` (endpoint). The compose demo delivers these to Mailpit (`http://localhost:8025`).

Reading/managing notifications goes through `notifications/NotificationRoutes.kt`, all under `authenticate` and scoped to the recipient via `requireNotificationRecipient` (recipient-only, no bypasses): `GET /api/v1/notifications` (list; sortable `id`,`timestamp`, default `-timestamp`; optional `wasSeen` filter), `GET /api/v1/notifications/{id}`, `POST /api/v1/notifications/{id}/seen`, `POST /api/v1/notifications/{id}/unseen`, `POST /api/v1/notifications/seen-all` (marks all the caller's unseen as seen; caller-scoped via `markAllSeen(recipientId)`), `DELETE /api/v1/notifications/{id}`. The endpoints are documented in `documentation.yaml`; the `notifications` table is created by `V13__create_notifications.sql`.

**Per-user feature flags (V46, v1.53.0).** The list (rows AND `total`) excludes notifications whose type belongs to one of the recipient's disabled features — the SPA's unread badge is the `total` of a pageSize-1 unseen query, so this one predicate keeps both honest. The type→feature mapping is the exhaustive `NotificationType.feature` extension in `notifications/Notification.kt` (`PASSWORD_CHANGED` and `CAREER_POSITION_STARTED_TO_USER` → `null` = never filtered — both ride ungated areas; the `when` forces every future type to pick a side — a `FeatureFlagsTest` case pins the values). The flags come from the caller's JWT claim (same ≤15-min staleness as route gating). **Deliberately unfiltered**: `GET /{id}`, seen/unseen, `seen-all` (may mark hidden rows seen — accepted), `DELETE`, and minting everywhere — a re-enabled feature reveals its backlog, still unseen unless a `seen-all` touched it.
